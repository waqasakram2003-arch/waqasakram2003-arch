Most developers hand over an application and hope it holds. I come at it from both sides: I write
the application, and then I attack it the way an outsider would — the auth bypass, the IDOR, the
injected parameter, the admin page that answers to a guessed URL. That second pass is the part most
small businesses never get, and it is where I spend my time.

I also teach this for a living. Over **500 students** have come through my classes on offensive
security, which keeps the fundamentals sharp in a way that building alone does not.

## Featured work

### 🔐 Vulnerable &amp; Secure Banking Application — *final year project*

A banking application built **twice**: once deliberately vulnerable, once hardened — so the same
feature can be attacked in one build and defended in the other, side by side.

The vulnerable build carries real, exploitable flaws: stored XSS leading to persistent defacement,
remote code execution, broken authentication and insecure direct object references. The secure build
closes each one and documents why the fix works. This is the clearest demonstration I have of the
whole loop — write it, break it, prove the fix.

**Stack:** Node.js · Express · MongoDB · React
